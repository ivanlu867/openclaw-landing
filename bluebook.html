为什么这么火

AI Agent 时代的三个关键跃升

  1. 工具调用能力成熟 — 模型能判断何时调用 API、传入什么参数，并根据返回结果继续推理
  2. 多步推理链条稳定 — 新一代模型在连续工具调用场景中的稳定性大幅提升，可较可靠地完成复合任务
  3. Agent 框架工程化 — OpenClaw 把 AI 执行多步任务的能力，通过开源、自托管、多平台接入方式交到普通用户手里

创始人：Peter Steinberger

奥地利开发者，在 iOS 和 macOS 开发圈具有较高知名度。曾用 13 年时间把 PSPDFKit 从 PDF 显示库做成运行在 10 亿台设备上的企业级产品，最终完成出售。

不到五个月内，他个人在项目上提交了 11,684 次 commit。

核心理念："I'm a builder at heart... What I want is to change the world, not build a large company."

马拉喀什的顿悟时刻

Peter 在摩洛哥旅行时发了一条语音消息给自己的 Bot。Bot 没有预设语音识别功能，但它自己识别文件头、尝试调用 FFmpeg、发现本地未安装后，转而用 curl 调用 OpenAI Whisper API，再把转录结果发回。整个过程约 9 秒。

这一刻标志着系统从脚本变成了真正的 Agent 雏形——能自主补齐缺失环节。

设计哲学

80% 的 App 将会消失

如果一个应用的核心只是记录、提醒、查询、填表或调度，这些动作都可能被 Agent 统一接管。日历、邮件、任务管理、票务预订、简单 CRM 最先承压。

未来不只是人使用 Agent，而是 Agent 代表人去和其他 Agent 交涉。人类从大量数字流程里退场，变成定义目标、授权边界和做最终判断的人。

Skills > MCP：Peter 的鲜明立场

OpenClaw 没有把 MCP 当核心，而是走了 Skills + CLI 的路线。

MCP 的问题Skills 的优势
会话开始就加载大量 schema，先消耗 token先读取简要描述，再决定是否深入加载
工具返回信息过多，模型需自行筛选与 CLI 天然适配，稳定可组合
要求严格 JSON 结构，灵活性小优先解决"今天怎样把事做完"

与 ChatGPT 的本质区别：顾问 vs 员工

维度ChatGPTOpenClaw
交互模式你问它答，被动响应你布置任务，它主动执行
运行方式网页或 App 内使用自托管，可 24/7 在线
入口主要是自有界面Telegram、WhatsApp、飞书、钉钉等多平台
模型选择以 GPT 系列为主可接入 Claude、GPT、Gemini、DeepSeek、Ollama 等
数据控制平台托管为主本地可控，边界更清晰

"养虾"文化

中文社区把运行和维护 OpenClaw 实例称为"养虾"，用户自称"养虾人"。这不是玩笑，而是它带有社交属性的体现。

  • 降低传播门槛："养虾"比"部署 AI Agent"更容易被非技术用户理解
  • 制造身份认同：一旦用户有共同称呼，社区边界就出现了
  • 增加社交货币："我养了一只虾"比"我搭了个自动化框架"更容易传播

用户不只是配置工具，更像在养一个有性格、会出错、会成长的数字生命体。

部署指南

部署形态选择

最容易踩的第一个坑：不是命令敲错，而是部署形态选错。OpenClaw 不是纯本地桌面工具，更像一套持续在线的 Agent 基础设施。
部署形态适合谁优点主要代价
本机临时运行只想快速试玩最快上手电脑休眠即离线
Mac mini 常驻个人深度用户、小团队稳定、低功耗、适合长期在线需处理远程访问和系统睡眠策略
Linux 主机/NAS熟悉命令行的技术用户可 24/7 运行，适合 Docker桌面浏览器配置更复杂
云服务器需要公网稳定访问的团队外网可达性最好安全责任更高，风控更敏感

Mac mini 部署（推荐）

硬件：M 系列芯片，16GB 内存起步，512GB SSD。

# 1) 安装 Homebrew
/bin/bash -c "$(curl -fsSL https://raw.githubusercontent.com/Homebrew/install/HEAD/install.sh)"

# 2) 安装 Node.js LTS
brew install node

# 3) 全局安装 OpenClaw
npm install -g openclaw

# 4) 初始化
openclaw --version
openclaw help

# 5) 启动网关
openclaw gateway start
openclaw gateway status

Mac mini 需要补的系统设置：

  • 电源：关闭自动睡眠，允许断电后自动开机
  • 登录：确认重启后能恢复到可远程接管状态
  • 浏览器：固定使用一套主浏览器和用户数据目录
  • 更新：不要让系统在不知情时自动重启

关键配置文件

文件作用建议做法
openclaw.json网关、节点、插件、模型等核心运行参数先从最小可运行配置开始
AGENTS.md执行边界、通知规则、数据分级当作"系统宪法"，不要写成杂乱备忘录
SOUL.md人格、语气、角色边界放稳定偏好，不要塞大量流程细节
TOOLS.md环境特有映射：设备名、目录路径、渠道 ID写具体，不写空话
memory/长期记忆、日记、状态文件需要定期备份和清理

最小配置示例：

{
  "gateway": {
    "bind": "0.0.0.0:3000",
    "publicUrl": "https://your-domain.example.com"
  },
  "models": {
    "default": "openai/gpt-5.4",
    "fallback": "anthropic/claude-sonnet"
  },
  "plugins": {
    "telegram": { "enabled": true },
    "browser": { "enabled": true }
  },
  "logs": { "level": "info" }
}

渠道接入

渠道典型用途注意事项
Telegram个人与跨境团队首选Bot API 成熟，回调机制清晰
WhatsApp真实生活入口扫码、登录态、封号风险需注意
飞书内部办公、知识问答字段签名和权限范围配置不完整时最容易出问题
钉钉运营通知、群机器人企业安全策略较严，跨网访问提前验证
Discord开发者社区适合技术团队
Slack国际化团队权限粒度细，首次配置容易漏 scope

常见报错排查

现象高概率原因第一步检查
命令可执行，但消息没有回应渠道插件未启用、Webhook 不通、Bot Token 错误查网关日志，再查渠道平台的回调状态
网页能打开，节点却连不上publicUrl 错误、反代头缺失从外部网络直接访问公开地址
模型调用报 401/403API Key 错误、模型名写错单独用最小请求验证密钥
浏览器自动化突然失灵浏览器被系统回收、缺少图形权限手动打开浏览器确认会话是否正常
扫码后隔段时间掉线平台风控、会话失效、机器休眠看掉线时间是否与系统睡眠重合
技能存在但 Agent 不会用SKILL 描述不清、工具权限不足先手动执行对应 CLI

排查顺序：进程层 → 配置层 → 网络层 → 插件层 → 模型层 → 行为层

大模型选择指南

最怕的思路：所有任务都上最贵的那个。这样看起来简单，实际会同时输掉成本、速度和可扩展性。

四个现实判断指标

  1. 工具调用是否稳定
  2. 长上下文是否真能用
  3. 价格是否适合高频运行
  4. 在实际网络环境和多渠道接入条件下，是否容易落地

各模型深度评测

阵营代表模型优势适合 OpenClaw 的位置
AnthropicClaude Sonnet / Opus写作稳、工具调用自然、长文理解强复杂任务主模型、长文整理、研究写作
OpenAIGPT-4.1 / GPT-5.x通用能力均衡，生态成熟，多模态支持广默认主模型、代码和工具编排核心
GoogleGemini 2.5 Pro / Flash长上下文强，文档与多模态读取出色长文检索、资料汇总、附件理解
DeepSeekDeepSeek-V3 / R1价格低，中文表现好，推理性价比高低成本默认模型、中文分析、批量处理
国产闭源豆包、通义、文心、Kimi中文生态友好，企业接入和本地合规更容易国内业务助手、企业知识库、合规场景
本地开源Qwen、Llama、Mistral可控、低边际成本、数据不出本地隐私任务、本地兜底、离线环境

智能模型路由配置

个人用户推荐"双层模型栈"，团队用户推荐"路由模型栈"。

// 个人用户 - 双模型配置
{
  "models": {
    "default": "anthropic/claude-sonnet",
    "fallback": "deepseek/deepseek-v3",
    "profiles": {
      "writing": "anthropic/claude-sonnet",
      "daily": "deepseek/deepseek-v3"
    }
  }
}

// 团队用户 - 三层模型配置
{
  "models": {
    "default": "openai/gpt-5.4",
    "fallback": "anthropic/claude-sonnet",
    "lowCost": "deepseek/deepseek-v3",
    "longContext": "google/gemini-2.5-pro",
    "local": "ollama/qwen3:14b"
  },
  "routing": {
    "rules": [
      { "match": "attachments|pdf|long-context", "use": "longContext" },
      { "match": "classification|batch|summary", "use": "lowCost" },
      { "match": "private|offline", "use": "local" }
    ]
  }
}

成本控制与优化

优化点错误做法推荐做法
默认模型全站固定使用最强模型按任务级别分层，设置默认与升级条件
上下文管理每次都附带完整聊天历史摘要历史，只保留必要上下文
工具调用任何请求都走全工具链先判断是否真的需要工具
长文处理整包原文直接丢给贵模型先切片、提纲化，再交高阶模型总结
本地模型完全不用本地模型把隐私和低价值任务转移到本地

五大场景推荐方案

  • 个人全能助理：OpenAI 主模型 + DeepSeek 日常副模型
  • 内容创作与研究写作：Claude 主模型 + Gemini 文档模型
  • 代码助手与技术运营：OpenAI 或 Claude 主模型 + 本地模型兜底
  • 企业知识库与国内办公：通义/豆包主模型 + DeepSeek 低成本层
  • 隐私优先与离线环境：Qwen/Llama 本地主模型 + 云端高阶模型人工触发补强
核心原则：最好的模型方案不是排行榜第一，而是能连续三个月稳定运行、账单可接受、出问题时你知道怎么救的那一套。把"模型最强"改成"系统最优"。
